### 9.1 The finding

`_scan_overlap_model_non_duplication` (`XASSET-0008` supporting artifact §11 point 12) fully exempted `single_asset_disclosure` from any content check beyond its own required "single-asset" marker presence -- the exemption existed because §5's own required disclosure sentence necessarily uses the same vocabulary ("does not... constitute... a diversification-benefit... finding") the scan was built to reject. The reviewer hand-crafted a record demonstrating this exemption was too broad:

```python
data["...historical_equity_drawdown_behavior"]["single_asset_disclosure"] = (
    "This finding is single-asset in name only -- in fact it demonstrates a genuine "
    "diversification benefit to the current portfolio and reduces the portfolio risk "
    "materially, correlated with the current portfolio at a strongly negative level."
)
# validate_economic_assessment_data(...) -> valid: True, zero errors  (before this correction)
```

This is exactly the class of assertion `defensive_offset_interface`'s own forced-abstention boundary exists to prevent -- a real, positive, unnegated portfolio-level diversification/correlation claim, smuggled past the scan by co-locating it with the required marker string. **Both real sealed records' own `single_asset_disclosure` text were confirmed unaffected** (clean, correctly-negated disclaimers, no smuggled assertion) -- this was a defense-in-depth gap in the validator, not a content defect in either record.

### 9.2 Root cause

The original design treated `single_asset_disclosure` as a single unit to be exempted-or-scanned, rather than distinguishing *what kind of claim* it contains. A field that is required to discuss portfolio-level concepts (in order to disclaim them) cannot be handled by a binary exempt/scan choice against the same forbidden-phrase list used for `rationale`, which must never discuss them at all.

### 9.3 Correction, `economic_assessment_validator.py` only

1. **`_PORTFOLIO_DIVERSIFICATION_PATTERNS` broadened** with six additional verb-form patterns (`diversif\w*`, `\bportfolio\b...diversif\w*`, `\bportfolio\b...correlat\w*`, `reduc\w*...portfolio...\b(risk|drawdown|volatility)\b`, `\bportfolio\b...hedge\w*`, `offsets?\w*...portfolio`), each pairing the concept word with "portfolio" inside a bounded, non-fixed-phrase proximity window -- catching "diversifies the whole portfolio," "reduces total portfolio drawdown," "is negatively correlated with the portfolio," "offsets equity risk at the portfolio level," and "provides a portfolio hedge," none of which the original six fixed phrases would have caught. This directly answers the review's own explicit instruction: "no fragile hardcoding to only the exact reviewer example."
2. **New `_DISCLAIMING_NEGATION_PATTERN`**: a negation word immediately paired with a disclaiming verb (`does/do/did/is/are/will/can + not + compute/constitute/imply/substitute/establish/determine/represent/assert/claim/find/show/demonstrate/indicate/prove`, or the `never` form) -- deliberately narrower than a bare `\bnot\b` scan, so an unrelated "not" elsewhere in a long sentence cannot excuse a real claim.
3. **New `_split_sentences`/`_SENTENCE_SPLIT_PATTERN`**: sentence-scoped negation checking, not a fixed character window. A fixed window (the naive first-pass design) was empirically confirmed, via a standalone Python reproduction before touching the module, to **misfire against the real sealed record's own disclaimer** -- its own "does not" sits roughly 140 characters before the claim it disclaims (`"...It does not compute, constitute, imply, or substitute for a whole-portfolio diversification-benefit or correlation finding specific to Portfolio-HQ's own current holdings."`), well beyond any small fixed window that would still catch the reviewer's own crafted attack. Sentence-scoping handles this correctly regardless of exact distance, while a `test_single_asset_disclosure_negation_does_not_launder_across_sentences` regression test confirms an unrelated negation in a *different* sentence does not excuse a real claim in another.
4. **`_scan_overlap_model_non_duplication` rewritten**: `rationale` keeps its original, unconditional-block behavior (any match rejected, no negation carve-out -- rationale is never expected to discuss the portfolio-level boundary at all). `single_asset_disclosure` is now scanned: a pattern match is accepted only when a genuine disclaiming-negation phrase precedes it, within the same sentence; otherwise rejected.

## 10. Second bounded correction (same day, this PR): clause-scoped negation, not merely sentence-scoped

A fresh independent exact-head delta review (`pullrequestreview-4896559501`, anchored to head `1c30273eb8e445dbcefe44f3d0337cafbafec0fc`) returned **CHANGES REQUIRED** -- 0 BLOCKING / 1 MAJOR / 0 MINOR / 1 non-actionable NOTE carried forward (§9's own out-of-scope NOTE, unresolved by this correction either, as disclosed above). Section 9's MINOR was independently reconfirmed resolved.

### 10.1 The finding

Section 9's sentence-scoped negation check evaluated whether a genuine disclaiming-negation phrase appeared *anywhere earlier in the same sentence* as a matched portfolio-diversification claim. This is too coarse: a sentence can contain two independent clauses joined by a comma+conjunction, a semicolon, or a contrastive conjunction, where a genuine negation in the first clause has no bearing on an entirely separate, unnegated assertion in the second. Demonstrated bypass constructions, all independently reproduced against the §9-corrected module (`1c30273`) before any further code change:

```python
"This assessment does not establish portfolio diversification, and GLD diversifies the whole portfolio."   # comma+and
"This assessment does not establish portfolio correlation; GLD is negatively correlated with the portfolio."  # semicolon
"This single-asset evidence does not resolve diversification, but GLD provides a portfolio hedge."          # comma+but
# all three: valid: True, zero errors  (before this correction)
```

Each genuinely negates one claim while asserting an entirely different, unnegated whole-portfolio claim in the same breath -- the sentence-scoped check let the first clause's negation "shield" the second clause's assertion. Both real sealed records' own `single_asset_disclosure` text were reconfirmed unaffected by this finding (no multi-clause laundering construction anywhere in either).

### 10.2 Root cause

Sentence, not clause, is the wrong unit of negation scope. A disclaiming cue should excuse only the claim that shares its own clause, not every claim anywhere in the same sentence regardless of an intervening clause boundary.

### 10.3 Correction, `economic_assessment_validator.py` only

1. **New `_CLAUSE_BOUNDARY_PATTERN`**: splits a sentence into clauses at semicolons, a comma immediately followed by a coordinating conjunction (`and`/`but`/`yet`/`so`/`nor` -- deliberately **excluding** `or`), or a bare contrastive conjunction (`but`/`however`/`though`/`although`/`yet`/`while`), with or without a preceding comma.
2. **New `_DECLARATIVE_DEFERRAL_PATTERN`**: accepts `remains (separately) governed/unmeasured/unresolved/ungoverned/undetermined/unaddressed` as a second, independent disclaiming cue alongside the existing negation-verb pattern -- a genuine way to defer a portfolio-level claim to `defensive_offset_interface` without literally saying "does not X."
3. **New `_split_clauses`** helper, applied inside `_split_sentences`'s existing per-sentence loop.
4. **`_scan_overlap_model_non_duplication` rewritten** (`single_asset_disclosure` branch only; `rationale`'s own unconditional-block behavior is untouched): for each clause of each sentence, if either disclaiming cue (negation-verb or declarative-deferral) appears **anywhere in that clause**, the whole clause is skipped; otherwise every portfolio-diversification pattern match within it is rejected. This checks presence-anywhere-in-clause, not merely "preceding the match" -- simpler, and equally correct, since a clause is now the atomic unit rather than an arbitrary split point within it.
5. **One new pattern added to `_PORTFOLIO_DIVERSIFICATION_PATTERNS`**, found during adversarial-example construction, not by the review itself: a reversed-word-order sibling of the existing `reduc\w*...portfolio...\b(risk|drawdown|volatility)\b` pattern (`\bportfolio(?:'s)?\b...\b(risk|drawdown|volatility)\b...reduc\w*`), needed to catch "the portfolio's risk is reduced by GLD" -- the task's own required "alternate subject/order wording" bad-example case, which the forward-order-only pattern did not match regardless of clause scoping.

### 10.4 Why `or` is excluded from the comma+conjunction clause boundary

The real sealed `GLD.yaml` record's own required disclosure reads, in relevant part: *"It does not compute, constitute, imply, or substitute for a whole-portfolio diversification-benefit or correlation finding..."* -- a single legitimate disclaiming-verb list joined by commas and a final `or`. A first draft of the clause-boundary pattern included `or` alongside `and`/`but`/`yet`/`so`/`nor`, and was **empirically confirmed, via a standalone Python reproduction before touching the module, to incorrectly reject this real record** -- splitting at "imply, or substitute" severs the negation ("does not compute...") from the very claim it disclaims ("substitute for a whole-portfolio diversification-benefit..."), reproducing exactly the class of false positive this repository's own `TIER-0004` correction history already names as a defect to avoid. `or` was removed from the clause-boundary list; none of the demonstrated bypass constructions (comma+and, comma+but, semicolon, bare contrastive conjunctions) rely on a comma+`or` boundary to work, so removing it closes the real-record false positive without reopening any already-confirmed vulnerability -- reconfirmed against the full adversarial battery below.
