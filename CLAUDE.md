## Portfolio Doctrine
- Book = **net equity** (gross `holdings.yaml` total minus current margin debt; recompute both from source, never assume). `holdings.yaml` is this repository's source of truth for the most recently synced gross value, margin debt, and net equity — no point-in-time figure is hardcoded in this document; always recompute from `holdings.yaml` directly.
- **Margin (revised 2026-07-13):** allowed within a fixed **1.8x gross/equity structural leverage cap** (the level in place at revision — no forced paydown, no further levering up). **30% margin-buffer floor, hard cutoff** — before any margin-funded buy, the system checks the most recently synced, Robinhood-displayed buffer against the 30% floor; if that synced buffer is already below 30%, the buy is blocked outright (no partial taper) and it's treated as a forced de-lever signal, same severity as the cash-tight guardrail: trim or pay down margin, don't wait it out. Independently of the buffer check, requested margin is clipped to the 1.8x leverage cap. **The system cannot calculate Robinhood's exact projected post-trade buffer from the data available to it** — there is no projected-buffer formula anywhere in this codebase; only the currently-synced buffer is checked, never a post-trade estimate. (`holdings.yaml`'s `margin.buffer_pct` is this repository's source of truth for the most recently synced buffer — no percentage is hardcoded in this document.) Because only the synced figure is checked, margin data must be freshly synced from Robinhood before it's relied on for any margin-funded decision, and synced again immediately after execution — a stale buffer is checked as if it were current, so sync discipline is load-bearing, not optional. Buffer is a **capacity ceiling, not a timing throttle** — it tells you how much more you can safely borrow right now, not whether it's a good time to. Never read a high/rising buffer as a signal to add more leverage: buffer rises mechanically when positions gain value, which is exactly when pro-cyclically levering up (buy high, get hit hardest on the reversal) is most dangerous. Margin is not a timing tool for increasing leverage: discretion may never lever up beyond a governed recommendation or the fixed cap, and never bypass the buffer floor or a repayment rule — but the operator may always decline a recommendation, use less margin than allowed, or repay more or sooner than required. Whether a rules-based, evidence-gated conditional rule can outperform this fixed posture is a separate, open research question (`GOV-0003`) — not yet adopted, not operational, and no license for market-view-driven lever-up in the meantime. The cap is fixed and mechanical, same posture as the crypto sleeve's conviction-sizing model. Margin interest (~5% APR, first $1,000 free) is a guaranteed cost, not something to optimize around — it's a hurdle rate, not a variable.
- Robinhood. Deposits and margin (within the cap above) are fuel.
- **Canonical destination architecture** (`targets.yaml`'s `destination:` list is config truth, PHQ-2026-02, superseding the prior five-tier T1/T2/ETF/band/spec structure): 37 rows, each with its own explicit `target_pct` — canonical v1.30, principal-approved under `PHQ-2026-01`. BTC/ETH/SOL each carry their own destination weight (2.0/1.5/0.5%), replacing the prior aggregate 10% crypto sleeve.

## Workflow (the only loop)
1. I deposit money and report buying power (or report available margin — check whether it's cash or margin before running the allocator; margin doesn't grow the book/target baseline the way cash does).
2. Positions are **live-priced automatically** (2026-07-13, extended to crypto 2026-07-14, extended to SKHY 2026-07-14): `holdings.yaml`'s `shares:` block (ticker → share count) and `crypto_shares:` block (coin → qty) are the source of truth for every normal position and coin — value = qty × latest Alpaca price, recomputed on every run, no manual resync needed for price moves. After a real buy/sell/trim changes a share count, paste `TICKER qty` lines → run `update-shares`; for a coin, `update-crypto-shares` (**merge mode; never `--replace` without my explicit confirmation**). BTC is manual until the reserve is rebuilt (no qty to track at $0) — paste screenshots or `TICKER value` lines → run `update-holdings`. Paste the margin screen too when it's changed → run `update-margin <debt> <buffer_pct>` (use Robinhood's own **displayed** buffer %, never derive it — see `allocate.py`'s `write_state()` comment for why).
3. Run `python allocate.py --cash X` for a cash deposit, or `--margin X` for margin-funded buying power (the two are gated differently — margin is clipped to the leverage cap and blocked below the buffer floor).
4. Present the recommendation table; I execute manually and confirm fills.
5. Sync share counts (and margin, if it changed) after execution.

**"Run a fresh allocation check" defaults to last-synced buying-power/margin state (2026-07-13).** Don't ask for a new buying-power/margin screenshot on every check — use the buying-power figure and margin state (debt/buffer) already on record in `holdings.yaml` unless I explicitly say something changed. I will proactively report deposits, withdrawals, margin draws/paydowns, or buffer changes when they happen; absent that, assume nothing moved. Portfolio value (gross/net equity) is computed fresh from all holdings on every run, **and since 2026-07-13 that includes live re-pricing** via `shares:` — no separate resync needed for ordinary price moves, only for a real share-count change (buy/sell/trim) or the BTC/margin manual paths above.
